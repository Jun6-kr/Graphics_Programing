## Implementation

### Frame 기반 Input 상태 추가

- 최대 256개의 Windows Virtual-Key Code를 기준으로 키 상태를 관리하는 `Input` 클래스를 추가했습니다.
- 각 키는 `Down`, `Up`, `Hold`에 해당하는 세 상태를 보관합니다.
- Actor와 Component가 `Input::Get()`으로 입력 상태를 조회할 수 있도록 전역 접근 구조를 사용했습니다.

```text
KeyState
├─ isKeyDown : 이번 Frame에 처음 눌림
├─ isKeyUp   : 이번 Frame에 처음 해제됨
└─ isKey     : 현재 계속 눌린 상태
```

### Win32 Message를 Input 상태로 변환

- `WM_KEYDOWN`, `WM_KEYUP`, `WM_SYSKEYDOWN`, `WM_SYSKEYUP`을 받아 `Input`에 Virtual-Key Code를 전달합니다.
- 현재 Focus가 Engine Window에 있을 때만 키 입력을 전달합니다.
- Window가 Focus를 잃는 `WM_KILLFOCUS`에서는 모든 키 상태를 초기화합니다.
- 같은 키의 반복 `WM_KEYDOWN`이 들어와도 이미 Hold 상태라면 `Down`을 다시 설정하지 않습니다.

```text
Windows Keyboard Event
→ Window Message
→ Engine::ProcessMessage()
→ Input::OnKeyDown() / OnKeyUp()
→ KeyState 갱신
→ Actor::Tick()에서 조회
```

### Frame 종료 시 일회성 상태 초기화

- Game Tick과 Rendering이 끝난 뒤 `ResetInputs()`를 호출합니다.
- `Down`과 `Up`은 한 Frame만 유지한 뒤 초기화합니다.
- `Hold` 상태인 `isKey`는 키가 실제로 해제될 때까지 유지합니다.

### TestActor 입력 확인

- `TestActor::Tick()`에서 `W` 키의 Down·Up·Hold 상태를 각각 조회합니다.
- 상태에 따라 Console에 입력 상태를 출력하도록 연결했습니다.
- `TGlobalAccessible`에는 전역 Instance 생성 여부를 확인하는 `IsValid()`를 추가했습니다.

## Learned

### OS 입력과 Engine 입력은 서로 다른 계층이다

- Win32 Message는 운영체제가 Window에 전달하는 Platform Event입니다.
- Engine의 `Input`은 이 Event를 Frame 단위의 일관된 상태로 변환합니다.
- Gameplay 코드는 `WM_KEYDOWN`을 직접 처리하지 않고 `GetKeyDown()`, `GetKeyUp()`, `GetKey()`를 통해 입력을 사용합니다.

```text
Platform Input
→ Engine Input State
→ Gameplay Query
```

### Down·Up과 Hold의 수명이 다르다

- `Down`은 눌리지 않았던 키가 눌린 순간의 한 Frame을 나타냅니다.
- `Up`은 눌렸던 키가 해제된 순간의 한 Frame을 나타냅니다.
- `Hold`는 누른 순간부터 해제될 때까지 여러 Frame 동안 유지됩니다.
- 이 구분을 위해 Frame 종료 시 `Down`·`Up`만 초기화하고 `Hold`는 유지합니다.

### UE와 XInput의 관계

- XInput은 Windows에서 Xbox 호환 Game Controller의 Button·Stick·Trigger 상태와 진동을 다루는 API입니다.
- 일반적인 Game Loop에서는 `XInputGetState()`로 Controller 상태를 조회하고 이전 Frame과 비교해 Down·Up·Hold 같은 Engine 상태를 만들 수 있습니다.
- 현재 CraftEngine 구현은 Win32 Keyboard Message를 사용하며 XInput을 사용하지 않습니다.
- Unreal Engine은 Hardware Input을 Gameplay에서 바로 사용하기보다 Player Input·Input Action·Mapping Context 같은 Engine 입력 계층으로 변환합니다.
- 따라서 `UE = XInput`이라기보다, Windows Gamepad 입력을 얻는 Platform API 중 하나로 XInput을 사용할 수 있고 Unreal은 그 위에 Mapping·Action 계층을 제공한다고 구분하는 편이 정확합니다.
- 현재 Unreal Engine에는 XInput 외에도 Platform과 설정에 따라 다른 입력 경로가 존재하므로 Unreal 입력 시스템 전체를 XInput 하나와 동일시하지 않습니다.

```text
현재 CraftEngine Keyboard
Win32 Message → Input KeyState → Gameplay

Windows Gamepad 확장 예시
XInputGetState → Controller State 비교 → Engine Input → Gameplay

Unreal Engine 개념 흐름
Hardware Input → Platform Input Layer → Player/Enhanced Input → Input Action → Gameplay
```

## Problem / Solved

### Gameplay가 Window Message를 직접 사용해야 하는 구조

**Problem**

- 기존에는 ESC 종료 처리 외에 Gameplay에서 Frame 단위 키 상태를 조회할 공통 입력 계층이 없었습니다.

**Solved**

- Win32 Message를 `Input::KeyState`로 변환하고 Actor가 Platform Message를 몰라도 Down·Up·Hold를 조회할 수 있게 했습니다.

### Focus를 잃은 뒤 Hold 상태가 남을 가능성

**Problem**

- 키를 누른 상태에서 Window가 Focus를 잃으면 해당 Window로 Key Up Message가 전달되지 않을 수 있습니다.

**Solved**

- `WM_KILLFOCUS`에서 `ResetAll()`을 호출해 모든 키 상태를 해제합니다.

## Decision

- Keyboard 입력은 Windows Virtual-Key Code 256개를 배열 Index로 사용합니다.
- Down·Up은 Frame 종료 시 초기화하고 Hold는 Key Up까지 유지합니다.
- Window Focus가 있을 때만 Keyboard Event를 Input에 전달합니다.
- Platform Message 처리와 Gameplay 입력 조회 사이에 Engine `Input` 계층을 둡니다.

## Issue

- 현재 입력은 Keyboard만 지원하며 Mouse와 Gamepad는 구현되지 않았습니다.
- `WM_SYSKEYDOWN`과 `WM_SYSKEYUP`을 처리한 뒤 바로 반환하므로 Alt 조합 등 기본 System Key 동작에 미치는 영향을 확인할 필요가 있습니다.
- TestActor의 입력 확인은 Console 출력만 수행하며 실제 이동이나 Action Mapping은 연결되지 않았습니다.
- Key Code를 직접 조회하므로 Gameplay 의미를 표현하는 Action·Axis Mapping 계층은 아직 없습니다.
- 사용자 요청에 따라 빌드·실행·테스트는 수행하지 않았습니다.
