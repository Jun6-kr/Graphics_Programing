## Learned

### 학습 초점: 정보가 어디에서 만들어지고 어떻게 변하는가

이 프로젝트의 학습 목표는 단순히 화면에 도형을 띄우는 것이 아니라, 각 객체가 어떤 정보를 가지고 있으며 그 정보가 Renderer와 그래픽스 파이프라인을 지나면서 어떻게 변하는지 이해하는 것입니다.

현재 한 Actor가 화면에 그려지는 정보 흐름은 다음과 같습니다.

```text
Actor / TransformComponent
│  position, rotation, scale
│  → World Matrix 생성
│
StaticMeshComponent
│  StaticMesh 참조
│  Shader 참조
│  Owner의 World Matrix 조회
│  → Render Command 제출
│
Renderer
│  Mesh·Shader·World Matrix를 Command로 보관
│  Mesh와 Shader 바인딩
│  World Matrix를 Constant Buffer에 복사
│  → DrawIndexed 호출
│
Input Assembler
│  Index Buffer로 Vertex Buffer의 정점을 선택
│  → Shader가 받을 정점 입력 구성
│
Vertex Shader
│  원본 정점 × World Matrix
│  → 변환된 정점 위치 생성
│
Rasterizer
│  삼각형 내부를 화면의 Fragment 후보로 변환
│  → 보간된 픽셀 입력 생성
│
Pixel Shader
│  각 픽셀의 출력 색상 계산
│  → 최종 색상 값 생성
│
Output Merger / RTV
│  출력 색상을 Render Target에 기록
│  → Back Buffer의 픽셀 변경
│
Swap Chain::Present
└─ Back Buffer를 Window에 표시
```

### 객체별 보유 정보와 역할

| 객체 | 가지고 있는 정보 | 전달하거나 만드는 정보 |
|---|---|---|
| `TransformComponent` | 위치·회전·크기 | World Matrix |
| `StaticMesh` | Vertex/Index Buffer, Index 개수 | Input Assembler에 지오메트리 제공 |
| `Shader` | Vertex Shader, Pixel Shader, Input Layout | 파이프라인에서 사용할 프로그램과 입력 해석 규칙 |
| `StaticMeshComponent` | Mesh·Shader 참조 | Mesh·Shader·World Matrix로 Render Command 제출 |
| `Renderer::RenderCommand` | Mesh·Shader·World Matrix | 한 번의 Draw에 필요한 CPU 측 데이터 묶음 |
| `Renderer` | D3D Device/Context, Render Target, Command 목록 | 바인딩·Constant Buffer 갱신·Draw Call 수행 |
| Vertex Shader | 정점과 World Matrix | 변환된 정점 위치 |
| Pixel Shader | Rasterizer가 만든 픽셀 입력 | 출력 색상 |

### Component에서 Draw Call이 발생한다는 표현의 구분

현재 `StaticMeshComponent::Draw()`는 D3D Draw Call을 직접 실행하지 않습니다.

```text
StaticMeshComponent::Draw()
→ Renderer::Submit()
→ Render Command 목록에 추가

Renderer::DrawCommand()
→ ID3D11DeviceContext::DrawIndexed()
→ 실제 Draw Call
```

따라서 현재 Component의 역할은 **그릴 정보를 생산하고 제출하는 것**이며, 실제 Draw Call 실행은 Renderer의 역할입니다.

상용 엔진에 가까워질수록 Component가 렌더링 정보를 소유하는 경우는 많지만, Component가 그래픽스 API를 즉시 호출하도록 만들 필요는 없습니다. 일반적으로 Renderer가 정보를 모은 뒤 Pass, 가시성, Material, 상태 변경 비용 등을 기준으로 정렬·배칭하고 Draw Call을 실행해야 전체 순서를 통제하기 쉽습니다.

### Component 순서와 Draw 순서

현재 Actor는 `componentList` 순서대로 각 Component의 `Draw()`를 호출하고, Renderer는 `renderCommandList`에 들어온 순서대로 명령을 처리합니다.

```text
Component Draw 순서
→ Render Command 제출 순서
→ 현재 Renderer의 Draw Call 순서
```

하지만 이후에는 제출 순서와 실제 Draw 순서를 분리할 필요가 있습니다.

- Opaque 객체: Shader·Material 등 상태가 같은 명령을 모아 상태 변경을 줄일 수 있습니다.
- Transparent 객체: 일반적으로 카메라에서 먼 순서대로 그려야 Blend 결과가 올바릅니다.
- 여러 Pass: Shadow, Scene, Post-process 등 목적별로 명령을 분류해야 합니다.

즉 Component는 필요한 정보를 제출하고, Renderer가 목적에 맞는 최종 순서를 결정하는 구조가 확장에 유리합니다.

### Unity 배칭과 개발자가 제어할 수 있는 범위

배칭은 여러 객체의 렌더링 작업을 묶어 Draw Call이나 상태 변경 비용을 줄이는 최적화입니다. 다만 `Shader가 같다`는 조건 하나만으로 항상 Mesh를 합칠 수 있는 것은 아닙니다. Material, Texture, Vertex Layout, Render State, Pass, 가시성 등의 호환 조건도 필요합니다.

Unity의 대표적인 배칭 방식은 다음처럼 구분할 수 있습니다.

- Static Batching: 움직이지 않는 여러 Mesh의 정점 데이터를 결합해 적은 Draw Call로 처리합니다.
- Dynamic Batching: 조건을 만족하는 작은 Mesh의 정점을 CPU에서 변환하고 묶습니다. CPU 처리 비용이 생깁니다.
- GPU Instancing: 같은 Mesh와 Material을 사용하는 여러 객체의 Instance 데이터를 전달해 한 Draw Call로 반복 렌더링합니다.
- SRP Batcher: Draw Call 자체를 무조건 합치는 기능이라기보다 Shader/Material 상태 설정 비용을 줄이는 방식입니다.

개발자가 제어할 수 있는 영역은 분명히 존재합니다.

- 객체를 Static으로 지정하고 Static Batching 사용 여부 선택
- 같은 Material과 Texture를 공유하도록 Asset 구성
- Texture Atlas 사용
- GPU Instancing 활성화와 Instance 데이터 설계
- Mesh를 수동으로 병합하거나 공간 단위로 그룹화
- Renderer에서 Render Command 정렬 기준 설계
- Profiler로 CPU, GPU, 메모리, Draw Call을 측정한 뒤 적용 여부 결정

엔진은 이 설정과 가시성·호환 조건을 바탕으로 실제 묶음 가능 여부를 판단합니다. Static Batching은 결합된 Mesh를 위한 추가 메모리를 사용할 수 있고, Runtime 결합은 CPU 비용이 들 수 있으며, 너무 크게 합치면 개별 Culling 효율이 나빠질 수 있습니다. 따라서 항상 적용하는 기능이 아니라 측정 결과에 따라 선택해야 합니다.

Unity 공식 문서에서도 Static Batching을 Build Time 또는 Runtime에 활성화할 수 있고, Runtime에는 `StaticBatchingUtility` API를 사용할 수 있다고 설명합니다. 즉 개발자가 설정과 API로 개입할 수 있지만, 최종 배치 분할은 Culling 등의 조건에 따라 엔진이 결정할 수 있습니다.

### Unreal의 Static·Stationary·Movable과 배칭

Unreal의 `Static`, `Stationary`, `Movable`은 기본적으로 Actor 또는 Component가 Runtime에 얼마나 이동·변경될 수 있는지를 나타내는 **Mobility 설정**입니다.

- Static: Runtime에 이동하거나 변경하지 않음
- Stationary: 일부 속성은 변경할 수 있지만 이동하지 않음
- Movable: Runtime에 이동·회전·크기 변경 등이 가능

Mobility 정보는 사전 계산 조명, Shadow, Cache와 여러 렌더링 최적화 가능성에 영향을 주지만, Unity의 Static/Dynamic Batching과 동일한 개념은 아닙니다. `Static이므로 자동으로 하나의 거대한 Mesh가 된다`는 직접 대응으로 이해하면 안 됩니다.

### Shader의 Runtime Compile과 Offline Compile

현재 프로젝트는 `Shader` 생성자에서 다음 함수를 호출합니다.

```cpp
D3DCompileFromFile(...)
```

따라서 실행 중 HLSL 소스 파일을 읽어 Shader Bytecode를 만들고, 그 Bytecode로 D3D Shader 객체를 생성합니다.

```text
현재 Runtime 경로
HLSL Source
→ D3DCompileFromFile
→ Shader Bytecode(ID3DBlob)
→ CreateVertexShader / CreatePixelShader
→ GPU에서 사용할 Shader 객체
```

Shader는 Build 단계에서 미리 컴파일할 수도 있습니다.

```text
Offline 경로
HLSL Source
→ Build Tool에서 .cso 등 Bytecode 생성
→ Runtime에 Bytecode 로드
→ CreateVertexShader / CreatePixelShader
```

Offline Compile을 사용하면 실행 중 컴파일 비용과 HLSL Compiler 의존성을 줄일 수 있습니다. 반면 Runtime Compile은 학습과 개발 중 Shader 수정 결과를 빠르게 확인하기 편합니다.

현재 프로젝트는 `.vcxproj`의 `FxCompile`로 HLSL을 Build할 뿐 아니라 Runtime에도 `D3DCompileFromFile`을 호출합니다. 즉 두 컴파일 경로가 함께 존재하므로, 추후 Runtime Compile을 유지할지 미리 생성한 Bytecode를 로드할지 정리할 필요가 있습니다.

### OBJ, FBX, Assimp, FBX SDK

OBJ는 정점, UV, Normal, Face와 Material 참조 등 정적 지오메트리를 표현하기 좋은 텍스트 기반 형식입니다. 하지만 Skeleton, Skinning, 계층 구조와 같은 애니메이션·변형 정보는 표현하지 못합니다.

FBX는 지오메트리뿐 아니라 Scene 계층, Material, Bone, Skinning, Animation 등 더 넓은 3D Asset 정보를 전달하는 데 사용됩니다.

도구 역할은 다음처럼 구분할 수 있습니다.

- Autodesk FBX SDK: FBX 기술을 읽고 쓰며 변환하는 C++ SDK
- Assimp(Open Asset Import Library): OBJ와 FBX를 포함한 여러 3D 형식을 공통 Scene 데이터 구조로 Import하는 라이브러리

따라서 향후 진행 방향은 `OBJ를 Assimp로 FBX로 변환한다`기보다 다음처럼 정리하는 편이 정확합니다.

```text
1단계
OBJ
→ Assimp Import
→ 정점·인덱스 추출
→ CraftEngine StaticMesh

2단계
FBX
→ Assimp 또는 Autodesk FBX SDK로 Import
→ Mesh·Material·Skeleton·Animation 추출
→ CraftEngine Runtime Asset
```

Assimp는 OBJ와 FBX를 모두 Import할 수 있지만, 공식 지원 목록에서 FBX Export는 experimental로 표시됩니다. 현재 학습 목표에는 파일 형식 간 변환보다, 외부 Asset을 읽어 엔진이 이해할 수 있는 Mesh와 후속 데이터로 바꾸는 Import Pipeline이 더 중요합니다.

## Decision

- Mesh와 Shader는 렌더링 책임을 가진 `StaticMeshComponent`가 참조합니다.
- Component는 Draw Call을 즉시 실행하지 않고 Renderer에 Render Command를 제출합니다.
- Renderer가 명령을 모아서 실제 파이프라인 바인딩과 Draw Call을 수행합니다.
- Shader 파일은 `이름 + VS/PS + .hlsl` 규칙으로 찾습니다.
- 동일한 Mesh와 Shader는 여러 Component가 `shared_ptr`로 공유합니다.

## Issue

- Render Command는 제출 순서대로 실행되며 Pass, Material, 거리, 상태 변경 비용에 따른 정렬이 없습니다.
- `StaticMeshComponent`는 Material 대신 Shader를 직접 보관하므로 Texture와 Shader Parameter를 함께 표현하지 못합니다.
- 같은 Mesh와 Shader를 사용하는 객체도 각각 Draw Call을 발생시키며 배칭과 Instancing은 구현되지 않았습니다.
- Shader를 MSBuild와 Runtime 양쪽에서 컴파일하는 중복 경로가 있습니다.
- Runtime Shader Compile 실패 시 Compiler Error Blob을 출력하지 않아 HLSL 오류 원인을 확인하기 어렵습니다.
- OBJ/FBX Import와 Engine Runtime Asset 변환은 아직 구현되지 않았습니다.
